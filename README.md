# API Management System

Microservice API management and topology visualization system built with FastAPI.

## Technology Stack

- **Runtime**: Python 11+
- **Framework**: FastAPI
- **Database**: PostgreSQL
- **ORM**: SQLAlchemy
- **API Documentation**: OpenAPI 3.0 (auto-generated by FastAPI)

## Prerequisites

- Python 11 or higher
- PostgreSQL 14+ (for local development)
- Docker (optional, for running PostgreSQL in container)

## Project Structure

```
api-management-system/
├── apimgmt/              # Main application code
│   ├── db/               # Database configuration
│   ├── models/           # SQLAlchemy models
│   ├── schemas/          # Pydantic schemas (DTOs)

├── main.py                # Application entry point
├── requirements.txt       # Python dependencies

```

## Local Development Setup

### 1. Start PostgreSQL Database

Using Docker Compose:
```bash
docker-compose up -d
```

Or use your local PostgreSQL installation and create the database:
```sql
CREATE DATABASE apimgmt;
```

### 2. Install Dependencies

```bash
pip install -r requirements.txt
```

### 3. Run the Application

```bash
python main.py
```

The application will start on http://localhost:8080

### 4. Access API Documentation

Once running, access the API documentation at:
- **Swagger UI**: http://localhost:8080/docs
- **OpenAPI Spec**: http://localhost:8080/openapi.json

## Testing

Run all tests:
```bash
pytest
```

Run specific test file:
```bash
pytest tests/repositories/test_api_repository.py
```

## API Endpoints

### Health Check
- `GET /` - Application root endpoint
- `GET /health` - Application health status

### Systems
- `POST /api/v1/systems` - Create system
- `GET /api/v1/systems/{id}` - Get system details
- `PUT /api/v1/systems/{id}` - Update system
- `DELETE /api/v1/systems/{id}` - Delete system
- `GET /api/v1/systems` - List all systems

### APIs
- `POST /api/v1/apis` - Create API
- `GET /api/v1/apis/{id}` - Get API details
- `PUT /api/v1/apis/{id}` - Update API
- `DELETE /api/v1/apis/{id}` - Delete API
- `GET /api/v1/apis` - List all APIs

### Endpoints
- `POST /api/v1/endpoints` - Create endpoint
- `GET /api/v1/endpoints/{id}` - Get endpoint details
- `PUT /api/v1/endpoints/{id}` - Update endpoint
- `DELETE /api/v1/endpoints/{id}` - Delete endpoint
- `GET /api/v1/endpoints` - List all endpoints
- `GET /api/v1/endpoints/api/{api_id}` - Get API endpoints

### Relationships
- `POST /api/v1/relationships` - Create call relationship
- `GET /api/v1/relationships/{id}` - Get relationship details
- `PUT /api/v1/relationships/{id}` - Update relationship
- `DELETE /api/v1/relationships/{id}` - Delete relationship
- `GET /api/v1/relationships` - List all relationships

### Health Checks
- `POST /api/v1/health/check/{endpoint_id}` - Check endpoint health
- `POST /api/v1/health/batch` - Batch health check
- `GET /api/v1/health/results/{endpoint_id}` - Get health check results
- `GET /api/v1/health/results` - Get all health check results

## Database Migration

We use **Alembic** for database migrations to manage schema changes over time. Alembic is a lightweight database migration tool for SQLAlchemy.

### Migration Workflow

#### 1. Initialize Alembic (if not already done)

```bash
# This has already been done in the project
# alembic init alembic
```

#### 2. Create a New Migration

When you make changes to your models (e.g., add a new table, modify a column), create a new migration:

```bash
# Auto-generate migration based on model changes
alembic revision --autogenerate -m "Description of the changes"

# Example:
alembic revision --autogenerate -m "Add created_at column to users table"
```

#### 3. Review and Edit Migration

Alembic will generate a migration file in `alembic/versions/`. Review this file to ensure it correctly reflects your changes:

```python
"""Add created_at column to users table

Revision ID: 1234567890abc
Revises: previous_revision_id
Create Date: 2024-01-01 00:00:00.000000

"""
from alembic import op
import sqlalchemy as sa

# revision identifiers, used by Alembic.
revision = '1234567890abc'
down_revision = 'previous_revision_id'
branch_labels = None
depends_on = None

def upgrade() -> None:
    # Add your upgrade logic here
    op.add_column('users', sa.Column('created_at', sa.DateTime(), nullable=True))

def downgrade() -> None:
    # Add your downgrade logic here
    op.drop_column('users', 'created_at')
```

#### 4. Apply Migration

Apply the migration to your database:

```bash
# Apply all pending migrations
alembic upgrade head

# Apply a specific migration
alembic upgrade 1234567890abc
```

#### 5. Rollback Migration

If you need to rollback a migration:

```bash
# Rollback to the previous revision
alembic downgrade -1

# Rollback to a specific revision
alembic downgrade 1234567890abc

# Rollback to the initial state
alembic downgrade base
```

### Migration Best Practices

1. **Always review generated migrations**: Alembic does its best, but it's not perfect. Always review the generated migration file before applying it.

2. **Test migrations in development**: Always test migrations in your development environment before applying them to production.

3. **Keep migrations atomic**: Each migration should focus on a single change. Avoid bundling multiple unrelated changes into one migration.

4. **Document migrations**: Write clear, descriptive messages for each migration to make it easier to understand the history.

5. **Backup before production migrations**: Always backup your production database before applying migrations.

### Generating Initial Migration

If you need to generate an initial migration for an existing database:

```bash
# Generate initial migration
alembic revision --autogenerate -m "Initial migration"

# Apply initial migration
alembic upgrade head
```
